## 4.8.6–4.8.7: real game friction measured from motion tracks (4.8.7 / build 51 installed; SHA256 276A9A208558E66EBF1A780F701981F6688D1105E69BC24240DB7B8887DC7C42)

APK: `OUTPUTS/apk/BitAim-v4.8.7-real-friction.apk`. 4.8.6 (`BitAim-v4.8.6-motion-track.apk`) only adds the motion recorder.

- **Motion tracks (4.8.6).** With debug recording on, every auto shot now logs each detected frame for 4 s after release (`"track"` in shots.jsonl; frames about 150 ms apart). Start and settled pictures cannot separate launch power from friction; positions over time can.
- **Friction law (tools/cv-test/TrackFit.java).** For discs sliding freely to rest, speed against remaining distance gave v = 1.26 x D^0.56 (49 samples). Exponent 0.5 means constant (Coulomb) friction and 1.0 means drag; the model used drag since v4.0. Constant friction fits with half the error (rms log 0.22 vs 0.49), and every shot was still moving after 3–4 s, which drag cannot do.
- **Trajectory fit (tools/cv-test/MathFit.java -Dtracks=true).** Simulating whole shots against the tracked frames gives friction 0.59 board widths/s² and launch speed about 10 x pull. Held-out error: constant friction 2.89 vs drag 3.12 striker radii.
- **Pot/miss check (OutcomeCalibrator, same 128 labelled shots).** Drag model 71.9% agreement, constant friction 76.6% (wrongly predicted pots 25 → 19). Launch per pull between 5 and 10 scores the same on the labels, so 8.5 was chosen between them.
- **Changes in 4.8.7.** PhysicsVerifier uses constant friction 0.60 (1/60 s slices, collisions exact inside a slice). Launch per pull went from 5.0 to 8.5. The auto pull is now the verified launch speed divided by 8.5, not a separate travel rule of thumb, so planning and shooting use the same physics. Validation, sweep and opener speeds use the real range (1.45–2.3 board widths/s = pull 0.17–0.27). Minimum pull went from 0.19 to 0.17, and breaks now pull 0.27. The chance estimate varies friction instead of drag. SOFT and HARD labels were moved to the new speeds.
- All regressions pass. SpeedBeamRegression's first speed went from 1.1 to 1.9 board widths/s, with the same checks.

## 2. Algorithm changes

- **Aim tolerance is measured for every validated route** (`Shot.aimMarginDegrees`, bracketed at ±0.5/1/2/4° inside `PhysicsVerifier.validate`, at most 8 extra solves).
- **Ranking by tolerance first** (`RoutePlanner.compare`): tiers are pot tolerating ≥1° effective, pot tolerating ≥0.5°, path opener, risky pot, manual cluster guide. Effective tolerance weights rail-dependent families down (direct 1.0, combination 0.75, striker cushion 0.6, coin cushion 0.5, cushion+combination 0.4) because the rail model is not calibrated. Pot+open-cluster routes keep their priority only when they tolerate at least 1°. Within a tier: stress passes, then pocket paths left afterwards (one-ply look-ahead), then simplicity, then score.
- **Wider ★ search**: up to three candidates per baseline sample and up to 12 validations ranked by the same comparator, so the suggested spot is the most forgiving one, not the highest raw score.
- **Positional play (`OpeningPlanner`, route kind 5)**: for each own coin the striker can reach cleanly, five cut offsets × three speeds are settled in the full model; the settled board is scored by the number of (own coin, pocket) direct paths from five baseline positions. A shot counts only if it adds a path or pots an own coin, never scratches and never pots an opponent. It is stress-tested at ±1° and bracketed for tolerance. Openers rank below forgiving pots and above risky ones, so a blocked board gets a plan instead of a message.
- `Shot.quality()` (score + 30 × tolerance) drives ★-versus-current and the tracker's route-switch hysteresis, so lines do not flip to a marginally higher score.

| practice-board-clean / shot2 / post-break (opening) | manual cluster guide | Pot + open paths +2 (9/9) from the centre of the opening cluster |

Early opener candidates allowed first contact on a known opponent disc; the ownership regression rejected that, and the final build only starts positional shots from an own coin, which is also what the tracker, refresh and ownership rules assume.

Regression suites (`verify-v4.1.ps1`: detection, planner geometry, team ownership, route, physics audit, queen rule, selection, pot+spread, speed beam, auto-play, focus/cluster and the picker view test) all pass with the new ranking; log in `test-results/v4.5-tests.txt`.

## 3. Stability and player experience

- **Planning no longer runs in `onDraw`.** v4.4 called the tracker (up to 21 physics solves per candidate, 387 ms on a PC for the dense opening frame, several times slower on the phone) on the UI thread every frame. v4.5 queues the newest frame to a dedicated planner thread with coalescing (an older frame is dropped when a newer one arrives), the ★ search runs on its own low-priority thread, and a result is applied only if it belongs to the frame on screen. While a new plan is pending the previous lines stay if the striker has not moved; otherwise a "Planning…" hint appears after 400 ms.
- **The overlay cannot take the game down**: `onDraw` and both planner threads are guarded; a fault logs and shows nothing for that frame. The tracker is accessed under one monitor and running passes are interrupted before a reset, so taps and striker loss never block the UI thread for a full plan.
- **Clearer HUD**: slightly larger hint text with a stronger shadow, a second smaller line for route details, and the tolerance badge (EASY ±N° / OK ±1° / TIGHT ±0.5° / RISKY) next to the alignment label. Openers show `OPEN PATHS • before → after pocket paths • N coins move • medium power, then pot next turn`. No filled shapes were added (the detector must keep ignoring the overlay).
- Settings screen kept as is apart from the version line, a footer explaining the badge and a How-to step 9.
- Automatic gestures stay OFF by default and never fire for openers or cluster guides.

## 4. Known limits and what still needs the phone

- Tolerance and pocket-path counts are nominal-model numbers (no spin, uncalibrated power, circular pocket capture). Rail families are down-weighted for that reason; a real rebound may still differ.
- Openers predict where coins settle at one of three model speeds; real power control decides whether the paths actually open. Collect before/after screenshots of a few openers to compare.
- `15:54:23` and `phone-capture-134613` still have no route or opener from the current spot and rely on ★.
- Live latency, the "Planning…" hint frequency and sustained match performance must be checked on the phone; the planner thread keeps the UI smooth but a dense board can still take longer than one capture interval to plan.
- Nothing here is a measured pot probability.
